# 工数見積りルール

ブリーフ出力時に、開発工数を1〜5段階で見積もる。
見積りはあくまで概算であり、正確な見積りではなく意思決定の材料として使う。

## 工数レベル定義

| Level | 目安期間 | 条件 |
|-------|---------|------|
| 1 | 半日〜1日 | 既存ツールの設定変更、単一スクリプト、Claude Code Skill作成。技術的な不確実性がほぼない |
| 2 | 2〜3日 | 複数スクリプトの組み合わせ、API連携1つ、簡易的なUI。使い慣れたツール・言語で完結する |
| 3 | 1〜2週間 | 簡易Webツール（認証なし）、外部API連携2つ以上、データ変換ロジックあり。小規模だが設計判断が必要 |
| 4 | 2〜4週間 | Webシステム（認証・DB付き）、複数画面、外部連携、テスト・デプロイ環境の構築が必要 |
| 5 | 1ヶ月以上 | 複数部門が使うシステム、複雑な権限管理、既存システムとの連携、段階的リリースが必要 |

## 評価軸

工数レベルは以下の4軸を総合して判断する。各軸の評価根拠をブリーフに記載すること。

### 1. 機能の技術的難易度

- 定型的な CRUD か、複雑なロジック・アルゴリズムが必要か
- 外部API連携の数と複雑さ（認証方式、レート制限、データ変換）
- リアルタイム処理、非同期処理、バッチ処理の有無

### 2. 利用ツール・構築ツールの難易度

- チームが使い慣れた技術スタックで実現できるか
- 新しいツール・フレームワークの学習コストが発生するか
- ローコード/ノーコードで代替できる部分があるか

### 3. 要件定義の難易度（利用人数・ステークホルダー）

- 1人向け → 要件は明確、フィードバックループが短い
- 2-5人 → 利用者間で要件のすり合わせが必要
- 6人以上・複数部門 → 部門間の調整、権限設計、ワークフロー設計が必要

### 4. 運用・インフラの複雑さ

- デプロイ先の環境構築が必要か（サーバー、DB、CI/CD）
- 監視・ログ・バックアップの要件があるか
- 継続的なメンテナンスが想定されるか

## カスタマイズ例

- チームのスキルセットに合わせて目安期間を調整する
- 社内の承認フローが重い場合、Level 3以上に「社内調整: +数日」を加味する
- 外部ベンダー連携がある場合、専用の評価軸を追加する
